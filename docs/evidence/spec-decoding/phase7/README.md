# T15 phase 7: full-size EAGLE-3 draft for Qwen3-4B (SpecForge, one RTX 4090, 2026-11-01)

Same `.venv-specforge` (SpecForge e3ab28d, SGLang 0.5.18) and the same target as phase 6:
Qwen/Qwen3-4B at revision 1cfa9a7208912126459214e8b04321603b3df60c. No trainer of our own:
features come from SpecForge `prepare_hidden_states.py`, training from `specforge train`, and the
SGLang model from `specforge export --to sglang`.

## Setup

- **Draft:** SpecForge's standard `configs/qwen3-4b-eagle3.json`, unchanged
  ([spec/configs/qwen3-4b-eagle3.json](../../../../spec/configs/qwen3-4b-eagle3.json)).
  Phase 6's reductions are undone: draft_vocab_size is 32000 and intermediate_size is 9728.
- **Data:** every UltraChat 200k `train_sft` prompt from the pinned shard that is eligible and
  not held out, 60,697 conversations. Each was regenerated by Qwen3-4B itself (SGLang, thinking
  off, greedy).
  - The run was split into four chunks in four GPU jobs; all 60,697 were regenerated, 0 failed
    and 0 skipped ([regen-summary](data/regen-summary.txt)).
  - Wall time: 5:01 + 46:23 + 46:19 + 43:14 = 2 h 21 min, including server startup.
  - The 128 held-out prompts are phase 6's `test_sft` prompts. A check by normalized-text hash
    found all 60,697 training rows disjoint from them
    ([batches manifest](data/batches-manifest.json)).
  - No second dataset was added. The held-out set is UltraChat, and the brief made a second
    dataset optional.
- **Vocab mapping:** computed once over all 60,697 conversations
  (`spec/t15_vocab.py`, max length 1024). The top 32,000 tokens cover 98.86% of target tokens
  ([log](data/vocab.log)).
- **Why offline, in batches:**
  - Online training does not fit this setup. SpecForge's managed-local online mode needs
    separate capture and trainer GPUs. External online mode would need the capture server and
    Mooncake kept alive between GPU jobs, which breaks the rule to release the GPU between runs.
  - Features take about 17.6 MB per conversation, about 1.08 TB in total, against a 40 GB share.
  - So `spec/t15_cycle.py` processes the data in 105 batches of 576 conversations (576 is a
    multiple of the capture batch of 16, because SpecForge drops a partial last capture batch).
    For each batch it:
    1. captures that batch's features (about 10.1–10.7 GB);
    2. trains it as one epoch of a single SpecForge run (`num_epochs` 105,
       `total_steps` 60,480, resumed from `{run_id}-latest`);
    3. deletes the features with `spec/t15_cleanup.py`, which refuses any path other than
       `.cache/t15/features*`.
  - One run with one cosine LR schedule spans all 105 batches
    ([config](../../../../spec/configs/qwen3-4b-eagle3-t15-full.yaml)).
- **Training settings:** batch 1, lr 1e-4, TTT length 7, flex attention, max_checkpoints 1.
- **Sizing from measured throughput:**
  - The smoke run (2 × 208 conversations, 04:50:46–04:54:14) measured about 41 s of feature
    capture and 63 s of training per 208 conversations, about 3.3 training steps/s.
  - Regen measured 7–8 conversations/s.
  - At those rates, one pass over all 60,480 usable conversations costs about 2.3 h of regen plus
    about 5.5 h of features and training. With about 1.3 h of benchmarks, T15 stays under the
    12 GPU-hour total, so the whole eligible shard was used, with no second pass.
  - That is 60,480 training steps, about 6× SpecForge's 10k-step reference recipe.
  - Each GPU job was capped at 6,600 s, under both the 4 h rule and the tool's 2 h
    background-task limit.
- **Training run:** four GPU jobs trained all 105 batches, through step 60,480.
  - Batch time was 173–207 s (features 6,088 s and training 13,688 s in total), 5.50 h of GPU
    time ([per-batch rows](train/cycle.jsonl)).
  - Peak project disk was 28.48 GB before a batch plus at most 10.72 GB of features: 39.2 GB of
    the 40 GB share.
  - The training-data acceptance rate in the step log rose from about 0.01 at step 100 to
    0.38–0.55 at the end ([metrics](train/train-metrics.log)). That is on training data, not
    held-out data.
  - The checkpoint is 3,055,871,403 bytes. The SGLang export is 436,900,562 bytes
    ([log](train/export.log)).
- **Machine:** 32 cores, with other sessions (Keel, PathWatch and others) running at the same
  time. They shared the CPU and queued for the same GPU lock, and the GPU was ours only during
  each job. Each per-batch row has load average and uptime before and after; load averages were
  about 2–4 during training.

## Main benchmark (phase-6 harness, 20:16:30–20:48:48)

- **Harness:** `spec/bench_tpot.py` via `spec/t15_gpu.sh bench`, one GPU job. SGLang 0.5.18 with
  `--mem-fraction-static 0.75`, the same 128 held-out prompts, greedy, at most 256 new tokens,
  closed loop at 1/4/16/64 requests in flight. EAGLE-3 settings are as in phase 6:
  `--speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`.
- **Run order:** two rounds of base, eagle3, public, with a server restart before each run.
- **Results:** 24 runs, all 3,072 requests completed, 0 failed. Output tokens per run were
  30,490–30,649 in every mode, so outputs are nearly but not exactly identical.
  Raw rows: `main/{base,eagle3,public}-r{1,2}.json`; summaries:
  [eagle3](main/summary.json), [public](main/summary-public.json); [log with load](main/bench.log).
- **Machine:** 32 cores, load average 1.5–2.7, other sessions running.
- **Public draft:** [AngelSlim/Qwen3-4B_eagle3](https://huggingface.co/AngelSlim/Qwen3-4B_eagle3),
  revision fd331e59626c8e95c392381a16ee59d518727fbb, Apache-2.0, 436,987,505 bytes
  (`scripts/fetch_angelslim_qwen3_4b_eagle3.sh`).
  - Its config names the class `Eagle3LlamaForCausalLM` (vLLM's name), which SGLang 0.5.18
    does not register.
  - `spec/t15_public_draft.py` therefore serves it from a view: a config with only that name
    changed to `LlamaForCausalLMEagle3`, and symlinks to the original weights. Its weight keys
    and shapes are identical to our export's.
  - A first attempt at this benchmark (19:44–19:56) stopped when that server failed to start.
    That attempt's round-1 files were overwritten by this complete rerun.

## Spec-config grid (declared before running, batch 1 and 64 only, 21:02–21:34)

- **Declaration:** [grid-declaration.md](grid-declaration.md) was written at 04:55 on
  2026-11-01 (file mtime), 16 hours before the first grid run. It names three configs besides the main default s3k1d4
  (steps : topk : draft tokens): s5k1d6, s2k1d3 and s3k4d8. No other config was run.
- **Harness:** as in the main bench (same draft, prompts, greedy, ≤256 tokens, a server
  restart before each run, two rounds of base, s5k1d6, s2k1d3, s3k4d8). 16 runs, 0 failed.
  Raw rows are in `grid/`, with summaries [s5k1d6](grid/summary-s5k1d6.json),
  [s2k1d3](grid/summary-s2k1d3.json) and [s3k4d8](grid/summary-s3k4d8.json), and a
  [log with load](grid/bench.log).
- **Machine:** 32 cores, load average 1.5–5.3, other sessions running.

Values are round 1 / round 2. Base TPOT was 9.31 / 9.32 ms at batch 1 and 13.48 / 13.47 ms at
batch 64. The s3k1d4 row is from the main bench above.

- **Batch 1:** tree drafting (s3k4d8, topk 4, 8 draft tokens) is fastest: TPOT 47% lower than
  no-spec, acceptance 2.59. Longer chains (s5k1d6) accept more but lose the gain to the
  extra draft steps.
- **Batch 64:** the shortest chain (s2k1d3) is best: TPOT 22–23% lower and throughput 16–18%
  higher. s5k1d6 and s3k4d8 are slower than no-spec there. s3k4d8's two rounds differ a lot
  at batch 64 (22.37 vs 16.14 ms), so its batch-64 number is not stable; both rounds are
  still slower than no-spec.
- So no single config wins: a server serving mostly single streams would pick s3k4d8, a
  loaded server s2k1d3. The main default s3k1d4 sits between them.
